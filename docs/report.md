# The JSON report

How to read the JSON report (`--json`, `--out`), the digest (`--digest`) and the page content files (`--content`). The Lighthouse part of a page is described in [lighthouse.md](lighthouse.md).

The JSON report is meant to be read by a person or a model. Write it to a file and ask Claude Code to read it:

```sh
node bin/pageaudit.js --sitemap https://example.com/sitemap.xml --limit 20 --lighthouse --out report.json
```

Then, in Claude Code: "read report.json and summarize the SEO and usability problems, most important first". Each page carries the issues the checks found, the Lighthouse summary and a `facts` object with what is on the page, so a suggestion can refer to the real title or headings. `facts` is `null` for pages that returned no HTML or whose HTML the checks could not process. Free text is capped to keep the file small: heading text and the Open Graph title, description and type at 120 characters (URLs at 2000), the page title, description and `h1s` at 300 characters, with at most 10 `h1s` and 40 headings. `generatedAt` is the time of the audit.

## Schema

The shape of the JSON report is described in [`schema/report.schema.json`](schema/report.schema.json) (JSON Schema, draft 2020-12), and every report starts with `schemaVersion`. The version goes up by one when a field is removed, renamed or changes its meaning, and stays the same when an optional field is added, so a script can check it before reading the rest. The tests validate reports from every kind of fixture against the schema, with no extra properties allowed, so the schema cannot drift from the code. Page issues name their page in `url` and site issues name theirs in `urls`, which the schema keeps apart as `pageIssue` and `siteIssue`. Both have an `id`.

The JSON report is meant to be handed to a human or an LLM for prioritizing fixes, so its shape is kept stable (`schema/report.schema.json` has the details):

```js
{
  schemaVersion: 1,
  generatedAt: '2026-10-15T08:00:00.000Z',
  pages: [{ url, finalUrl, status, redirects: [{ url, status, location }], issues: [...], facts, content, lighthouse }],
  site: [...],                    // site issues
  origins: [...],                 // how each origin's robots.txt treats AI crawlers, and its platform
  skipped: [{ input, source, reason }],
  coverage: { tool, settings, urls, links, notRun: [{ check, reason }] },
  rules: { [type]: { title, why, fix } },
  lighthouseAudits: { [id]: { description, learnMore } },
  summary: { pages, errors, warnings, infos }
}
```

`lighthouse` is only present on pages Lighthouse ran for, `content` only on pages written with `--content`, and `lighthouseAudits` only when an audit is described.

`coverage` says what the audit looked at, so a model can tell "not found" from "not looked for": the pageaudit version, the `settings` that change what is collected (with the defaults filled in), how many URLs were `found` and `audited` (and whether every sitemap file was read), with `--check-links` how many link targets were `checked` and how many were left past the cap, and `notRun`, the checks that did not run with the reason. `lighthouse` and `links` are listed when they were not asked for, and `orphan-page` when the audit could not tell orphan pages apart, such as after a `--limit` cut.

`status` and `finalUrl` are `null` when the page could not be fetched at all.

## Issues

Every issue, page or site, has an `id`, a `type`, a `message` and a `context`. Where the check found a single element it also has a `selector` (a CSS path), the element's `html` and its `parentHtml` (capped at 500 and 200 characters, `parentHtml` is left out when the parent is `html`, `head` or `body`). Length checks add the measured `actual` value and the `expected` limit. The top-level `rules` object explains each issue `type` that occurs in the report once, as `{ title, why, fix }` (the same wording as the HTML report), so a model knows what a finding means and how to fix it. The `id` is built from the page, the type and the selector, so it is the same on every run as long as the page keeps its structure. Adding an element earlier in the page changes the ids after it, so compare ids within one report.

Every page issue has the same shape, so `report.js` has no per-check special cases:

```js
{
  id: 'missing-alt-3f2a9c1e',     // type plus a hash of the page and the element, see src/issue-id.js
  url: 'https://example.com/',    // the page, as given in the input
  type: 'missing-alt',            // machine-readable identifier
  severity: 'error',              // 'error' | 'warning' | 'info'
  category: 'accessibility',      // 'seo' | 'accessibility' | 'performance' | 'best-practice'
  source: 'https://www.w3.org/WAI/tutorials/images/decorative/',
  message: 'Image missing alt attribute',
  context: '<img src="/a.jpg">'   // snippet for locating the problem
  // optional: selector, html, parentHtml (the element behind the issue), actual and expected (length checks)
}
```

Site issues have the same fields except that `url` is replaced by `urls`, the list of pages involved.

## AI crawlers and platform

The top-level `origins` list says, for each origin the audited pages ended up on, how its `robots.txt` treats AI crawlers, so a model can tell a site kept out of AI search from one that only opted out of training. `robotsTxt` is `ok`, `missing` (no file, everything allowed), `unreachable` or `failed`. `aiSearch` covers the crawlers that find pages for AI search answers (`OAI-SearchBot`, `Claude-SearchBot`, `PerplexityBot`) and `aiTraining` the tokens for training only (`GPTBot`, `ClaudeBot`, `Google-Extended`, `Applebot-Extended`, `CCBot`), each as `allowed`, `blocked` or `partial` over the audited pages of the origin, and `null` when the file could not be read. `contentSignal` is the `Content-Signal` value for every crawler, such as `search=yes, ai-train=no` from Cloudflare's managed `robots.txt`, or `null`. Pages kept from an AI search crawler while Googlebot may crawl them are also an `ai-search-blocked` issue.

Each `origins` entry also has `platform`, the shop or site builder most of the origin's audited pages run on, as in their `facts.platform`, or `null`. The digest has no page facts, so this is where a model reading it learns that the fix for a Shopify store goes in the theme.

## Page facts

Each page that returned HTML has a `facts` object:

| `facts` field                              | Meaning                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`, `description`, `h1s`, `canonical` | The values the site checks compare (the canonical is resolved to an absolute URL, and `h1s` leave out script, style and noscript text)                                                                                                                                                                                                                                                         |
| `lang`, `viewport`, `robots`               | The `lang` attribute and the viewport and robots meta tags                                                                                                                                                                                                                                                                                                                                     |
| `robotsHeader`, `nosnippetElements`        | The `X-Robots-Tag` header as sent, rules for every crawler included, and how many span, div and section elements have `data-nosnippet`                                                                                                                                                                                                                                                         |
| `headings`                                 | Outline of `{ level, text, excerpt }`, at most 40 headings, text capped at 120 characters (script, style and noscript are left out) and the `excerpt` (the first words under the heading) at 200                                                                                                                                                                                               |
| `wordCount`                                | Words of visible body text (script, style and noscript are not counted), a rough measure of depth                                                                                                                                                                                                                                                                                              |
| `mainText`                                 | The visible text of `<main>` or `<article>` (else the body without nav, header, footer and aside), cut at 1500 characters                                                                                                                                                                                                                                                                      |
| `links`                                    | `{ internal, external, nofollow }` counts of http(s) links. `www.` is treated as the same site                                                                                                                                                                                                                                                                                                 |
| `linkSamples`                              | The first 25 page links as `{ href, text, internal, nofollow }`, with the anchor text, or the alt of an image link, capped at 120 characters. Script, style and noscript are left out                                                                                                                                                                                                          |
| `images`                                   | `{ total, missingAlt }`                                                                                                                                                                                                                                                                                                                                                                        |
| `imageSamples`                             | The first 20 images as `{ src, alt, context }`: absolute address, alt text (`null` if missing) and the figure caption or the words around the image                                                                                                                                                                                                                                            |
| `openGraph`, `twitterCard`                 | Open Graph title, description, image, type and url, and the Twitter card type                                                                                                                                                                                                                                                                                                                  |
| `jsonLdTypes`                              | The `@type` values of valid JSON-LD blocks, at most 20. Invalid JSON-LD is ignored                                                                                                                                                                                                                                                                                                             |
| `hreflang`                                 | The first 100 `<link rel="alternate" hreflang>` tags in `<head>` as `{ lang, href }`, the href resolved to an absolute URL where possible                                                                                                                                                                                                                                                      |
| `jsonLd`                                   | Up to 10 typed JSON-LD nodes as `{ types, name, authors, publisher, datePublished, dateModified, sameAs }`: `name` is the headline, else the name, `authors` (at most 5) and `publisher` are names with `@id` references to other nodes of the page resolved one step, and `sameAs` holds the first 5 profiles. Text is kept as written, so HTML entities some CMSs put in it (`&#8226;`) stay |
| `dates`                                    | `{ published, modified, lastModified, sitemapLastmod }` as written: the first JSON-LD `datePublished` and `dateModified`, else `article:published_time` and `article:modified_time` (then `og:updated_time`), the `Last-Modified` header (on a page built for every request often just the time it was sent) and the `<lastmod>` of the sitemap entry that listed the page                     |
| `author`                                   | The `author` meta tag, else the JSON-LD authors of the first node that has any                                                                                                                                                                                                                                                                                                                 |
| `products`                                 | Up to 10 Product or ProductGroup nodes (a group read with its variants) as `{ types, name, brand, sku, gtin, mpn, image, offers, shipping, returnPolicy, rating }`. `offers` has `count`, `lowPrice`, `highPrice` (prices Google can read: a dot for decimals), `priceCurrency`, `availability`. `shipping` and `returnPolicy` are `offer`, `organization` or `null`. Not read in an ItemList  |
| `platform`                                 | `{ name, theme }` of the shop or site builder the page runs on: Shopify (`theme` is the theme the shop's theme was made from, such as Dawn), WordPress (`theme` is the theme's folder), Wix, Squarespace or Webflow. `null` when the HTML shows none of them                                                                                                                                   |

## Digest

The report grows by 10 to 15 KB per page, most of it the page `facts`, so beyond a few dozen pages it is more than a model reads well in one go: a 100-page audit of a real site made a 1.3 MB report. Most of the issues in it are the same problem repeated on pages that share a template. `--digest` also writes a short form of the report for Claude to read first, and the report stays complete next to it:

```sh
node bin/pageaudit.js --sitemap https://example.com/sitemap.xml --lighthouse --out report.json --digest report.digest.json
```

Then: "read report.digest.json, rank the problems most important first and look up the details in report.json by url and type where you need them". The digest holds:

| Field               | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `about`             | One paragraph on how the digest was cut and how to read it, for the model                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `report`            | `path` of the full report relative to the digest (`null` without `--out`), its `schemaVersion` and `generatedAt`                                                                                                                                                                                                                                                                                                                                                                                            |
| `origins`           | The same as in the report                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `coverage`          | The same as in the report                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `summary`, `scores` | The report totals, the pages by their worst issue (counting the site issues that list them, as in the HTML report) and the average Lighthouse scores                                                                                                                                                                                                                                                                                                                                                        |
| `skipped`           | The first 5 inputs that were not audited, and `moreSkipped`                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `findings`          | One entry per issue type, page and site issues together, worst first: `title`, `why` and `fix`, how many `pages` and `hits`, the 3 most common `messages` with their page counts (one message on many pages is one pattern, even when each page has its own element), and up to 5 `variants`. A variant is one element (same selector) or value (same context) with its message, markup, measurement, how many pages it is on and the first 3 of them. A logo without alt text on every page is one variant |
| `lighthouseAudits`  | The failing Lighthouse audits by id, on most pages first, with the worst score and the 3 worst pages. Inputs that redirect to one page count once                                                                                                                                                                                                                                                                                                                                                           |
| `pages`             | One line per audited page: status, issue counts, `finalUrl` when it redirected, with Lighthouse the scores, `omittedAudits` and the number of `lighthouseWarnings`, and with `--content` the page's Markdown file as `content`, relative to the digest                                                                                                                                                                                                                                                      |

Counts are never cut, only lists, and `moreMessages` and `moreVariants` say how many were left out. The one exception is Lighthouse: the report already keeps only the worst failing audits of each page, so `lighthouseAudits` counts pages among those. Text from the page, such as a long URL, is cut at 2000 characters. The digest is for triage: it lists the problems the checks found, not the page content, so judging content, intent or navigation still needs the `facts` in the full report or the `--content` files, and without `--out` there is no full report to look in. A missing issue type means nothing was found only on pages the checks could inspect: a page that answered with an error, was not HTML, could not be fetched, made a check fail or was cut at 2 MB has an issue saying so. Only `pages` grows with the number of pages, at about 150 bytes each, and the digest of that 100-page audit was 44 KB. The shape is described in [`schema/digest.schema.json`](schema/digest.schema.json), and `digestVersion` follows the same rules as `schemaVersion`.

## Page content

The `facts` hold the outline of a page, the first words under each heading and the first 1500 characters of its main text. That is enough to judge how a page is organised and where its key information sits, but not what it covers or whether it is right. In a blind test on three long articles, Claude with only the report could say "add this, if the body does not already cover it", while Claude with the full text found the missing topics, outdated advice, a broken link and terms used one way and defined another. `--content <dir>` writes the main content of each page as Markdown, one file per page:

```sh
node bin/pageaudit.js --sitemap https://example.com/sitemap.xml --out report.json --digest report.digest.json --content content
```

Then: "read report.digest.json, pick the pages that matter most and judge their content from the files in content/". Each file starts with front matter that names the page (`url`, `finalUrl`, `title`), says which part of it was read (`area`: `main` for `<main>` or `role="main"`, `article`, or `body` without its nav, header, footer and aside, the same part as `mainText`) and has `truncated: true` when the HTML was cut at 2 MB. The rest is that part of the page as Markdown: headings, paragraphs, lists, tables (a spanning cell repeated in each column it covers, the caption first), code, quotes, links resolved to absolute URLs and images with their alt text and their address when it is a web address or a data URI (an image with no alt attribute says so). A table used for layout is read cell by cell, and page text that Markdown would take for markup is escaped. Callouts inside the main part, such as an `<aside>` note, are kept. It is the HTML as served, before scripts run, like every page check: on a page built in the browser it holds what a crawler that does not run scripts sees. Files are named after the URL as given, such as `web.dev_articles_inp.md`, in input order, with `-2`, `-3` for a clash or a name another file in the folder already has, so the same input gives the same names, and they are written as the pages are audited, into a hidden `.pageaudit-` folder inside the content folder. A file pageaudit did not write is never replaced, so a page whose name such a file took during the audit fails the run like a file that cannot be written. A page the Markdown fails on keeps its checks and is named on stderr. A page that returned no HTML gets no file. Each page that got one names it in `content` in the JSON report (relative to the `--out` file, or to the working directory when the report is only printed) and in its digest line (relative to the digest). Once the inputs are read, the folder is made if needed. Only when the audit is done do the new files replace the ones an earlier audit wrote there, so it holds only the pages of this audit, and a run that fails or is stopped leaves the earlier files as they were. A hidden folder such a run left is removed by the next one. Other files in it are left alone.
